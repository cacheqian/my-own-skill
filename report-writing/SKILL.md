# 汇报改写

让第一次接触项目的读者快速理解：这是什么、解决什么问题、现在做到哪里、下一步要做什么。用文字给判断，用表格展开可比较的信息，用图解释关系。直接交付可汇报的成稿。

本 Skill 提供写作与呈现方法，业务事实以本次材料为准。参考样本只用于理解表达方式，不把其中的数字、进度、名称或目标带入新材料。

## 接收材料与确定主线

- 阅读本次材料及其实际包含的表格、截图、画板。以当前材料为准；读不到的资源明确说明，不能声称已学习其视觉风格。
- 从上下文判断读者、汇报目的和交付位置。默认面向没有项目背景的管理者；技术评审则保留支撑取舍的技术细节。只有影响主线的缺口才提问，其余先完成能确定的部分。
- 用户指定的问题、章节及子问题逐项保留，在其结构内改写。未指定时，可沿“是什么与价值 → 整体机制 → 现状与差距 → 下一步”组织；短材料无需凑齐章节。
- 先分清事实、判断、建议和规划，再压缩表达。保留影响判断的数字、时间窗口、单位、指标口径、适用范围、关键条件与来源。缺失信息不补造；原文冲突不静默选边。

## 决定每份信息放在哪里

| 信息的主要用途 | 优先形式 | 处理方式 |
|---|---|---|
| 定义、结论、判断、取舍、请求决策 | 短文字 | 一句话点题，必要时补理由与条件 |
| 能力建设、职责边界、方案差异、业务数据、交付计划 | 原生表格 | 同一维度横向比较，每行一个对象 |
| 层级、协作关系、执行与反馈、依赖或演进路径 | 关键画板 | 一图回答一个整体问题，节点与关系均有含义 |
| 产品操作入口、实际交互与结果示例 | 必要截图 | 紧邻对应功能，短标题指出应看什么 |
| 趋势、分布、数量差异 | 数据图表（按需） | 只有比表格更易发现规律时才使用 |

正文给出从表格或图中得到的判断，不逐项复述。信息少时可以全部用文字；能用简单表格说清的内容不升级成画板。数据图表与截图也不能成为绕过精简要求的办法。

## 文字：只留下影响理解与决策的信息

- 开篇先给核心定义或当前判断；首次介绍项目，可用“面向谁，解决什么问题，以什么方式交付什么”写一句定义。没有证据的价值写成目标或预期。
- 各节直接进入结论、差距或关键动作，省去“以下将介绍”“从多个维度赋能”等铺垫。用“支持什么、覆盖哪里、还缺什么”替代抽象形容词。
- 每段一个意思。并列价值可以用“**价值短语：**具体收益”的短列表；不要把所有段落拆成碎片。
- 首次出现的专业词以括号给出简短解释，后文沿用同一称呼。业务汇报只保留能解释能力、边界和取舍的实现细节。
- 先合并结构上的重复，再压缩句子；不设固定压缩比例。“初步、内测、待验证、计划”等词若决定事实边界，必须保留。
- 区分能力建设、系统执行与业务效果。已接入不等于全场景可用，执行成功不等于效果达标，计划目标不等于已完成。仅按本次材料能支持的程度下结论。
- 涉及外部依赖时，区分自建、复用、接入与定制，写清本项目新增的能力、可控制范围及仍依赖谁；材料未说明的贡献不推定为自建成果。
- 多方案、多模式或多业务线汇报，分别说明各自目标、共用能力和专属交付；同名指标仍需核对统计范围与分母，不合并不同口径的目标或结果。
- 技术框架可按“基础来源 → 关键适配 → 专项优化 → 支撑的能力”组织，材料缺少的环节不补造。管理汇报重点说明改造带来的能力与边界，技术评审再展开影响取舍的细节。

## 表格：让读者快速比较

- 表头反映真实问题，不用“相关情况、其他说明”等空泛字段。常见表型见 [表格与改写示例](references/report-patterns.md)，按需选择，不强制照搬。
- 每行保持同一对象粒度，每列保持同一比较维度；比较方案时覆盖相同问题。默认选最少的有效列，通常 2～4 列足够。
- 第一列用短标签，说明列承载主要信息；单元格用短句或少量并列项。若一格塞进多个主题，拆行或重新分组。
- 状态用“已支持／验证中／规划中”等明确文本；可搭配符号，但不能只靠颜色或勾号表达成熟度。
- 建设进展写实际能力与范围；规划写交付物。责任人、时间、验收标准只在材料提供或任务需要时列入，不能为了填满表格而编造。
- 数据统一单位与精度，标明统计期和口径；不同口径不直接比较，明细与汇总不一致时标明待核实。正文保留最影响判断的数字，明细放表内。

## 格式与视觉

- 标题层级、短段落、加粗和表格承担主要导航。默认以两级标题组织，确有必要再加三级；沿用用户指定的编号。
- 加粗用于核心判断、关键数字和行标签，避免整段加粗。需要时用一个浅色提示块突出核心定义或总判断，不为每节加装饰卡片。
- 默认白底、浅灰分区、蓝色主链路、橙色规划项；全篇同一种含义使用同一颜色，并保留文字标签。用户或团队既有规范优先。
- **短篇汇报通常用 1～2 张关键图；具体数量按独立解释价值与篇幅决定。** 先用一张讲清整体逻辑，其余图仅展开不能被已有图或表格替代的问题。没有独立解释价值则不画，不为套用默认数量删除有用的现有图。
- 每张图有一句可读懂的标题、明确方向与边界。节点用“模块名＋短说明”，关系线表示真实的流程、依赖或反馈；不要把模块清单机械连成流程。
- 尽量让核心逻辑在单幅图的一屏内闭环。图太密时先删减和归组，将次要细节移入表格或引用，不通过缩小字号、无限放大画布或不断加图解决。
- 需要实际制作或修改图、排版原生文档时，先读 [视觉与排版规范](references/style-reference.md)。其中提供可按平台与品牌规范调整的默认建议。

## 交付与检查

- 用户只要求改写时，在当前对话交付完整稿；指定文件或在线文档时，使用相应平台能力完成授权范围内的交付。只读参考文档只用于学习，不回写、不评论。
- 按交付平台选择可用能力；飞书环境可分别使用 lark-doc、lark-whiteboard 处理正文与画板。已有图表、数据与链接优先复用。调整已有画板时核实其内容与承载的信息，不为套风格丢失信息。
- 没有画板能力时，可以提供可编辑 Mermaid 或明确标注的制图稿；不能把节点说明或代码块声称为已创建的原生画板。没有真实截图时不生成界面冒充产品证据。
- 写回在线文档后重读，核对正文、表格、引用与画板；实际制图后预览检查字号、重叠、裁切、连线和色彩一致性。遵守用户及工作区的实际写入范围，本 Skill 不扩大权限。
- 最后检查：读者能否迅速抓到主张；指定问题是否完整；事实与规划是否分开；关键数据和条件是否保留；文字、表格、图是否各有用途；全部画板在正常阅读尺寸下是否清晰。
- 将经验沉淀或发布为通用 Skill、模板或示例时，只保留抽象方法与明确标注的虚构材料。检查正文、示例、元数据和附件，不收录内部地址、真实人员或账号、项目 ID、业务数据、内部架构细节、密钥或原始内部截图；虚构示例不沿用真实标识或成组业务数字。正常汇报中的事实与证据链接按用户要求及交付范围保留，不因方法通用化而擅自删除。
- 最终只交付成稿或成果链接，简短说明必要的证据缺口；不附长篇改写过程。只有实际完成核对后才报告“已验证”。
